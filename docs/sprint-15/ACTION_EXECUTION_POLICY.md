# Sprint 15 — Action Execution Policy

## Location
`internal/application/ai/execution_policy.go`

## Purpose

The Action Execution Policy defines which commerce actions AI can suggest, whether confirmation is required, and how AI-suggested actions flow through the execution pipeline.

## Policy Overview

```
AI Output (Intent)
    ↓
Intent Resolution
    ↓
Action Allowlist Check
    ↓
Action Construction (authenticated actor + server-resolved tenant)
    ↓
CommerceActionRuntime
    ↓
   ├─ Identity Protection (override actor)
    ├─ Tenant Resolution (override tenant)
    ├─ Parameter Validation (untrusted AI params)
    ├─ RBAC Authorization (server-side)
    ├─ Usage & Credits (reserve → execute → consume/release)
    ├─ Idempotency Check
    ├─ Confirmation Policy (server-side)
    ├─ Handler Dispatch (through Provider Orchestrator, never direct)
    ↓
Result
```

## Action Classification

### READ_ONLY Actions

These can be executed without confirmation:

| Action                  | Requires Confirmation |
|-------------------------|----------------------|
| SEARCH_LISTINGS         | No                   |
| GET_LISTING             | No                   |
| COMPARE_LISTINGS        | No                   |
| CHECK_AVAILABILITY      | No                   |
| GET_ORDER               | No                   |
| GET_RESERVATION         | No                   |
| GET_FULFILLMENT_STATUS  | No                   |

### LOW_RISK_MUTATION Actions

These require confirmation:

| Action                   | Requires Confirmation |
|--------------------------|----------------------|
| CREATE_LISTING           | Yes                  |
| UPDATE_LISTING           | Yes                  |
| PUBLISH_LISTING          | Yes                  |
| PAUSE_LISTING            | Yes                  |
| RESUME_LISTING           | Yes                  |
| CREATE_ORDER             | Yes                  |
| CANCEL_ORDER             | Yes                  |
| CREATE_RESERVATION       | Yes                  |
| CANCEL_RESERVATION       | Yes                  |
| MODIFY_RESERVATION       | Yes                  |
| ADJUST_INVENTORY         | Yes                  |
| CREATE_MARKETING_CAMPAIGN| Yes                  |

### FINANCIAL Actions

These require confirmation + special handling:

| Action              | Requires Confirmation |
|---------------------|----------------------|
| INITIATE_PAYMENT    | Yes                  |

## Confirmation Enforcement

Confirmation requirements are determined by:
1. The `ConfirmationPolicy` interface (Sprint 7's `DefaultConfirmationPolicy`)
2. The action's `ActionCategory` (READ, WRITE, FINANCIAL)

The policy is **always server-side**. The AI cannot:
- Set `confirmation_state` to "approved"
- Override whether an action requires confirmation
- Skip the confirmation step

## Flow for Confirmation-Required Actions

```
AI suggests CREATE_ORDER
    ↓
Orchestrator constructs CommerceAction (confirmation_state = "not_required")
    ↓
CommerceActionRuntime.Execute
    ↓
ConfirmationPolicy.RequiresConfirmation → true
    ↓
Return ActionResultRequiresConfirmation
    ↓
Orchestrator returns confirmation request to user
    ↓
User confirms (authenticated)
    ↓
Orchestrator re-executes with confirmation_state = "approved"
    ↓
CommerceActionRuntime executes the action
```

## Idempotency

All actions initiated via AI are wrapped with an idempotency key generated by the orchestrator. Duplicate AI requests that produce the same intent + parameters are deduplicated via `IdempotencyStore` (Sprint 7).

## Usage & Credits

Every AI-initiated commerce action consumes credits through the existing Usage Service:

1. Orchestrator resolves usage policy for the action type
2. CommerceActionRuntime reserves credits
3. On success → consume
4. On failure → release

AI-specific usage policies (cost per AI action) can be added via the existing `UsagePolicy` system without a separate AI credit system.
